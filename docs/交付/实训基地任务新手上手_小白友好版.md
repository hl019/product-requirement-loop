实训基地任务 · 新手上手（小白友好版）
  给谁看：第一次接触「GitHub 接任务」的实训基地同学。
一句话机制：接任务 → 交设计 → 等批准 → 写代码交「三件套」→ 四人审 → 计分。
这篇是什么：把《实训基地协作指南.md》翻译成「人话版 + 实战版」，照着走一遍就能跑通第一单。规则细节以《实训基地协作指南.md》《任务贡献指南.md》为准。

两个最容易误解的点（先记住）：
1. 你评论 /claim 不会立刻把任务给你——只有维护者把 Design 合并后、再评论 /accept @你，任务才算真正到你名下（汇总表「接取人」栏才会写你的名字）。
2. 同一账号同时只能接 1 个任务。想换题必须先 /cancel。
1. 开始之前：准备 3 样东西
1.1 一个 GitHub 账号
- 没有就注册：打开 https://github.com/signup ，邮箱 + 用户名 + 密码即可。
- 记住你的用户名（比如 hl019），后面很多地方要填它。
1.2 把仓库 Fork 一份到自己的账号
这套机制走 fork 模式：你不直接改原仓库，而是先把它复制一份到自己账号下，在自己的 fork 里改，再推 PR 给上游仓库：
- 打开 https://github.com/hongwei-2026/product-requirement-loop
- 点右上角 Fork → Create fork（全部保持默认即可）
- 完成后你的账号下会多一个同名仓库（页面左上角显示 你的用户名 / product-requirement-loop）
  fork 只需要做一次。以后每次接任务，都在自己 fork 里开新分支。
1.3 一个能收信的邮箱
- Design 方案交上去后，要用邮件通知维护者（他靠邮箱盯审批）。任何你常用的邮箱都行。
  不需要装任何软件。有 GitHub 账号 + fork 一次 + 有邮箱，就够了。
2. 选一道题（第一次选最简单的）
1. 打开 Issue #7 总览 或 实训基地任务汇总表。
2. 找「接取人」那一栏是 —（空）的题。
3. 第一次建议选 #1：[Task][Easy] 工作台顶栏展示当前 LLM 摘要，10 分、最简单，适合练手跑通全流程。
4. 点进 Issue，先把正文从头读完——里面写明了这题要做什么、交付物规范、验收标准。
  难度与积分速览：简单 10–15 · 中等 25–35 · 难 50–60 · 特难 70–90。具体以 Issue 正文「积分」为准。
3. 实战：跟着 #1 走一遍
以 #1 顶栏展示 LLM 摘要 为例，从接题到计分，一共 6 步。
第 1 步 · 登记意向（评论 /claim）
- 打开 Issue #1，拉到页面最底部，在评论框单独一行输入：
/claim
- 点绿色的 Comment 发出。
- 机器人会回复你下一步提示。此时汇总表里接取人仍然是空的，这是正常的。
第 2 步 · 写设计文档（Design）
- 进入你 fork 的仓库的 docs/designs/ 目录。
- 打开 _TEMPLATE.md（模板），点右上角 Raw 或直接复制它的内容。
- 在你 fork 的 docs/designs/ 里新建一个文件，文件名按 #任务号-简短英文.md，例如：
#1-topbar-llm-summary.md
- 把模板填完。模板一共 7 节，你只要把「背景与问题 / 目标 / 方案摘要 / 影响面 / 验收标准」写清楚就行，其他照抄。
- 不要在这个文档里塞完整代码，最多放伪代码 / 接口草图（Design 是「设计合同」，不是实现）。
第 3 步 · 开 Design PR + 发邮件
1. 开分支（在你 fork 的仓库里）：点分支下拉（main）→ 输入 design/#1-topbar-llm-summary → Create branch。
2. 开 PR：切到该分支，点 Compare & pull request，确认方向是 hongwei-2026:main ← 你的用户名:分支（一般自动就对）。
  - 选 PR 模板：选 Design（描述框上方会有模板选择）。
  - 标题：[Design] #1 顶栏展示 LLM 摘要
  - 正文写：Related to #1（不要写 Fixes，否则没实现就提前关 Issue）。
3. 发邮件给 feizi_050920@qq.com，主题写：
  [Design] #1 <你的GitHub用户名>
  正文附三样：① Issue 链接 ② Design PR 链接 ③ 你的 GitHub 用户名。
第 4 步 · 等批准（/accept）
- 维护者审查并合并你的 Design PR 后，会在 Issue #1 里评论：
  /accept @你的GitHub用户名
- 这之后，汇总表「接取人」栏才会写上你的名字。
- ⚠️ Design 没合并前，不要去催 /accept——机器人会拒绝。也不要提前开实现 PR。
第 5 步 · 写代码 + 交「三件套」
Design 合并、你被 /accept 之后，开始动手：
1. 开分支（同样在你 fork 的仓库里）：feat/#1-topbar-llm-summary。
2. 写代码，改完提交。
3. 开 PR：选模板 Implementation，标题 [Impl] #1 顶栏展示 LLM 摘要，正文写 Fixes #1。
4. 正文里必须交「三件套」，缺一不可：
  - ① 代码（本 PR）
  - ② 演示视频链接（可公网打开，如 B 站 / 飞书云文档·妙记 / 录屏分享）
  - ③ 截图 ≥ 2 张（改前 / 改后，直接贴在正文）
5. 严禁：代码、截图、视频里出现 API Key / .env 内容。
第 6 步 · 等四人审 + 合并 + 计分
- 四位必审人全部 Approve + 自动检查变绿后，维护者合并 PR。
- 合并后维护者评论 /score 10（按完成质量微调）。
- 你的名字出现在计分板 / 排行榜，这一单就算完成了。
  补材料：如果审的人让你补视频/截图，补完后在 PR 里评论 /recheck 重跑检查。
4. 新手最常踩的坑（FAQ）
Q1：我 /claim 了，汇总表怎么还没我名字？
A：正常。要等「Design 被合并」+「维护者 /accept @你」两步之后才写。光 /claim 只是登记意向。
Q2：能同时接两道题吗？
A：不能。同一账号同时只能 1 个进行中任务。想换题先评论 /cancel 或 /release。
Q3：Design 还没合并，能先开实现 PR 吗？
A：不能。实现 PR 的作者必须已经是 /accept 锁定的 Assignee，否则门禁 task-lock 会拦下，不算数。
Q4：我一个月没推 PR 会怎样？
A：关联的 Design / Impl PR 超过 30 天无更新 → 系统自动释放，接取人清空，任务重开，别人能接。
Q5：实现 PR 的正文里 Fixes 和 Related to 有什么区别？
A：Fixes #N 会在 PR 合并时自动关闭该 Issue，实现 PR 用它。Design PR 还没真正实现，所以用 Related to #N，避免提前关 Issue。
Q6：我发错命令了，比如多写了一个字怎么办？
A：命令必须单独成行、原样写（如 /claim）。发错一般机器人不会执行，重新发一条正确的即可；拿不准就私聊维护者。
Q7：提交后检查一直是红的怎么办？
A：先看 PR 下方检查项的名字（比如 delivery-artifacts 表示缺视频/截图），对照补上，再评论 /recheck 重跑。
